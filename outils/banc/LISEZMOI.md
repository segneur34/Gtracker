# Banc de test

Scripts Node qui pilotent un Chrome sans fenêtre (ou la WebView du téléphone) par le protocole DevTools, pour éprouver l'application dans un vrai navigateur sans la manipuler à la main. Ils complètent les tests unitaires (`npx vitest run`), qui tournent sous Node sans navigateur : ni les pages montées, ni la mémoire du navigateur (OPFS), ni les sons ou le rejeu en temps réel. Aucune dépendance : Node 22 ou plus (`fetch` et `WebSocket` natifs). Chaque script, ce qu'il éprouve et s'il rend un verdict : `SCRIPTS.md`.

## Mise en place

1. Node 22 ou plus et Google Chrome (ou Chromium).
2. `npm ci` à la racine du dépôt (Vite et l'application ; le banc lui-même n'a aucune dépendance).
3. Chrome est cherché à ses emplacements ordinaires : sous Windows `%ProgramFiles%`, `%ProgramFiles(x86)%` et `%LOCALAPPDATA%` (`Google\Chrome\Application\chrome.exe`), puis `where chrome` ; sous macOS `/Applications` et `~/Applications` (Google Chrome, Chromium) ; sous Linux `google-chrome-stable`, `google-chrome`, `chromium`, `chromium-browser` sur le `PATH`. Ailleurs : `CHROME=<chemin du programme>`. Introuvable, le lanceur le dit et sort en code 2. macOS et Linux : chemins relus, pas essayés sur le poste de développement (Windows 11).
4. Depuis un worktree sans `node_modules` (un dossier de travail à côté du dépôt), le lanceur prend le premier `node_modules` qui contient Vite en remontant les dossiers, comme `outils/verif.mjs`.

Ports : le lanceur sert l'arbre de travail sur 4195 et le commit d'avant sur 4196, ses Chrome partent de 9480 ; 5174 est le serveur de développement de l'utilisateur (`npm run dev`), à ne jamais prendre ; 4190 est refusé par Chrome (« bad port »).

À la main, pour un script seul : un serveur `node <dépôt>/node_modules/vite/bin/vite.js --port 4195 --strictPort --host 127.0.0.1` chargé une fois dans un navigateur ; un Chrome sans fenêtre sur un **profil neuf**, `"<chemin de Chrome>" --headless=new --remote-debugging-port=9480 --user-data-dir=<brouillon>/chrome-profil --window-size=1400,1000 --no-first-run about:blank`, fermé par `Browser.close` ; puis `MSYS_NO_PATHCONV=1 BASE=http://127.0.0.1:4195 node outils/banc/<script>.mjs 9480 …`, chemins au format du système (`DOM.setFileInputFiles`).

## Lancer un passage

`node outils/banc/passe.mjs <noms…> --avant HEAD` : joue les scripts nommés sur l'arbre de travail (« après ») et sur le dernier commit (« avant »), et compare leurs relevés. Sans nom, le passage courant du registre ; `--pages voile,surf` choisit par page touchée ; `--tous` les joue tous. Le passage dure de 1 à 20 min selon les scripts.

Le tableau final, une ligne par script : durées des deux côtés ; résultat (`ok`, `N échecs` comptés sur les lignes « ÉCHEC », `code N`, « délai dépassé ») ; erreurs de console (nouvelles entre parenthèses) ; relevé `identique` ou `différent` (le diff suit, 20 lignes, avec le chemin des deux relevés). Code 1 dès qu'un script échoue ou diffère. Un script « à verdict » contrôle lui-même des chiffres attendus (`check`, puis « Tout passe. » ou le nombre d'échecs) ; les autres ne prouvent qu'une neutralité par rapport au commit d'avant (`SCRIPTS.md`, « Verdict ou neutralité »).

## Lanceur

`node outils/banc/passe.mjs [noms…] [--pages a,b] [--tous] [--avant <commit>] [--scripts-par-cote] [-j N] [--sans-reseau] [--gpx <dossier>] [--brouillon <dossier>] [--temps k] [--captures] [--garder] [--sans-cache] [--nettoyer-avant] [--chrome <port>] [--port <port Vite>] [--langue fr|en|es]`

- Langue : Chrome est lancé en `--lang=fr-FR` (et `--accept-lang`), sans quoi l'application, qui prend la langue de l'appareil faute de réglage, partirait dans celle du Chrome sans fenêtre. `--langue en` ou `--langue es` lance Chrome en `en-GB` ou `es-ES` ; les scripts cliquent par texte français, le passage courant reste donc en français. Seuls `tailles` et `langues` marchent dans les trois langues : ils lisent la langue de la page et cliquent par le texte traduit (`lib/langue.mjs`) ; `langues` relève les textes restés en français et les largeurs (`passe.mjs langues --langue en -j 1`).

- Sélection : des noms, ou `--pages` (étiquettes du registre `scripts.mjs` : voile, surf, enregistrer, bibliotheque, planification, statistiques, profil, reglages, accueil), ou `--tous` ; sans rien, le passage courant, la liste `PASSAGE_COURANT` de `scripts.mjs` (voile et surf, sans réseau, sans fichier à fournir ; une trentaine de scripts, environ 18 min 30 à `-j 1`) ; il ne comprend pas `tailles` (20 min), à jouer par son nom ou `--pages` quand le changement touche la mise en page, le thème ou Réglages. `--sans-reseau` écarte les scripts marqués `reseau`. Un script marqué `manuel` dans le registre n'est lancé que s'il est nommé, la raison est dans le tableau.
- Côtés : « après » est l'arbre de travail, servi sur 4195. Avec `--avant <commit>`, « avant » est ce commit, dans un worktree `<brouillon>/avant-<commit>` (gardé d'un passage à l'autre ; `--nettoyer-avant` le retire ; à la fin d'un passage avec `--avant`, les copies `avant-<commit>` des autres commits, laissées par les passages précédents dans le même brouillon, sont retirées, la jonction d'abord), son `node_modules` relié à celui du dépôt (jonction sous Windows, où un lien symbolique demande les droits d'administrateur ; lien de dossier ailleurs) puis retiré, jamais par une suppression récursive, servi sur 4196. Les deux serveurs ont leur config générée dans `<brouillon>/vite/` (cache à part, polices `@fontsource` permises) et sont préchauffés sur un profil jetable. Par défaut, les scripts de l'arbre de travail tournent des deux côtés (neutralité de l'application) ; `--scripts-par-cote` donne à l'avant ses propres scripts (reprise d'un script : `--avant HEAD --scripts-par-cote`).
- Exécution : un Chrome par script et par côté, profil effacé avant, ports à partir de 9480 (`--chrome`) ; `--port` déplace les serveurs Vite (après sur ce port, avant sur le suivant), pour plusieurs passages en même temps avec chacun son `--brouillon`, fermé par `Browser.close` ; `-j 4` scripts en parallèle, avant et après en même temps ; les scripts `solo` (temps réel) passent seuls, à la fin. Chrome tourne sans bac à sable (`--no-sandbox`) seulement lancé en root (conteneur Linux). Fin d'un processus : `taskkill /T` sous Windows (`child.kill` n'y tue que le processus direct : Vite, esbuild et Chrome survivraient), ailleurs le groupe du processus (`SIGTERM`, puis `SIGKILL` 2 s plus tard). Le script reçoit `BASE`, `MSYS_NO_PATHCONV=1`, `TEMP`, `TMP` et `TMPDIR` vers son dossier de travail, `DUMP` s'il le lit, `SHOT` et le dossier des captures avec `--captures`. Délai : 10 min par défaut, ou le `delaiMin` du registre (15 à 45 min pour les mesures longues et `tailles`), puis « délai dépassé ».
- Horloge : `--temps k` pose `TEMPS=k` aux scripts marqués `accelerable` du registre (`notes`, `carte-direct`, `materiel-fin`, `rendus`), dont la page vit alors k fois plus vite (`lib/horloge.mjs`, « Bibliothèque ») ; `--temps 10` est le réglage conseillé pour un passage (sortie inchangée au bruit déjà connu près). Avec `--scripts-par-cote`, c'est le registre du commit d'avant qui dit si son script lit `TEMPS` (sans registre à ce commit, aucun) : la reprise d'un script pour l'horloge se prouve ainsi, l'avant à temps réel. Restent à temps réel (sortie changée à `TEMPS=10`) : `balises` (écarts entre bips au centième), `notification` (durée de la pause lue à 0,1 s de la page).
- Relevés : `<brouillon>/releves/<commit>/<script>.txt` (côté après : `<commit>-apres`, ou `<commit>-modifie` pour un arbre non commité), sortie normalisée (`HOTE`, `TRAVAIL`, `DEPOT`, `BROUILLON` ; masques communs : `UUID`, `DATE` pour un horodatage ISO ou un nom de session daté, `EPOQUE` pour un instant en ms, `N ms` pour une durée ; puis les masques du registre), sortie d'erreur, code de sortie et texte du `DUMP`. Le relevé « avant » est réutilisé tant que commit, script (et `lib/` s'il l'importe), arguments et `TEMPS` n'ont pas changé (« relevé réutilisé ») ; `--sans-cache` le refait (un relevé raté par lenteur resterait sinon) ; `tailles` n'est jamais réutilisé.
- Sortie : sur la sortie d'erreur, une ligne par script fini ; puis le tableau (durées, résultat : ok, N échecs comptés sur les lignes « ÉCHEC », code de sortie ; erreurs de console comptées sur les lignes `EXCEPTION:` et `error:` ; identique, différent ou avant absent), le diff de chaque relevé différent (20 lignes) avec le chemin des deux relevés, les erreurs de console nouvelles, le temps du passage et de sa mise en route. Code 1 dès un échec ou un code non nul côté après, une erreur de console nouvelle, une différence ou un script inconnu ; les échecs de l'avant sont montrés sans compter (un script neuf sur l'ancienne application).
- Brouillon par défaut `gtracker-banc` dans le dossier temporaire du système (`%TEMP%` sous Windows) ; `--garder` y laisse profils et dossiers de travail. Ctrl+C tue serveurs et Chrome et retire la jonction. Les chemins passés aux scripts se forment par `join` (`node:path`), jamais avec un `\\` écrit en dur.
- Charge : à plusieurs de front, le lanceur pose `BANC_CHARGE` (scripts de front × côtés) et `lib/cdp.mjs` multiplie par lui le plafond de `waitFor` (pas ceux de `settle` et `go` : une page jamais immobile les atteint à chaque appel, et multipliés ils ont fait passer des scripts de 1 min à 8 min et au délai de 10 min) ; les scripts qui ont leurs propres attentes fixes (`bench`, `familles`…) peuvent encore échouer sur une machine chargée. Filet : avec `-j` au-dessus de 1, un script en échec d'un seul côté (ou sans comparaison d'avant) est rejoué une fois, seul, avant d'être déclaré ; le tableau le dit (« rejoué seul : réussi » ou « échec aussi »). Un échec des deux côtés n'est pas rejoué. Un relevé d'avant qui porte un échec n'est jamais réutilisé du cache.

## Programme Windows

`node outils/banc/passe.mjs [noms…] --exe bureau/sortie/Gtracker-win32-x64/Gtracker.exe -j 1` (le programme se fabrique par `npm run exe`, à refaire après un changement de l'application ou de la coquille). Sans `--avant` : « avant » est la référence, Chrome sur `vite preview` qui sert le `resources/dist` du programme (les mêmes fichiers : seule la coquille change), « après » une instance du programme par script, sur un profil à part, page servie en `https://gtracker.localhost` (masqué comme `HOTE` dans les relevés). Relevés dans `releves/exe-chrome` et `releves/exe-programme`, jamais réutilisés.

- Mode d'essai de la coquille : `GTRACKER_BANC=1`, `GTRACKER_PROFIL=<dossier>`, `--remote-debugging-port` (refusé sans le mode d'essai), `--lang=fr-FR` ; le lanceur ajoute `--force-device-scale-factor=1` et `--hide-scrollbars`, les conditions de Chrome sans fenêtre : sur l'écran à 125 % du poste, une bordure de 1 px mesure 0,8 px et la barre de défilement (15 px) décale de 7,6 px les centres mesurés. Dans ce mode la page fait 1382 × 904, comme celle de Chrome sans fenêtre lancé à 1400 × 1000. Le script se branche sur la page par `BANC_WS` (`/json/list`), une instance par script (une seule fenêtre par instance).
- Aucun réseau réel dans le programme en mode d'essai : ses requêtes passent par la coquille, pas par le réseau du navigateur ; `Network.setBlockedURLs` y bloque bien, mais `Fetch` (fausses tuiles, faux lieux) ne voit rien, et les hôtes non bloqués sont refusés par la coquille (journal « réseau refusé »). Écartés : `shots`, les scripts `dev` (ils importent les sources dans la page : le programme porte le build de production), ceux qui importent `lib/tuiles.mjs` ou `lib/lieux.mjs`, le contexte isolé. Un script qui ne bloque pas le réseau charge les vraies tuiles sous Chrome et rien sous le programme : « © OpenStreetMap » contre « Carte… » dans la liste des sessions (`cacher`), sans lien avec la coquille.
- Un script qui échoue côté Chrome sur le build de production (`profil`, `apropos`, `tutoriels`, `import-session`) échoue de même côté programme : l'écart se lit entre les deux colonnes, pas contre une réussite.
- Un observateur de plus sur la page du programme relève les violations de la politique de contenu, les requêtes qu'elle bloque et les erreurs du journal que `connect` n'écoute pas, avec le journal de la coquille (autorisations, liens, fermeture) : une ligne « programme » sous le tableau, code 1 pour une violation.
- Même brouillon court que d'ordinaire (`%TEMP%\gtracker-banc`) : le profil d'une instance sous un chemin long (le dossier de travail d'une session de Claude) fait échouer le Cache API de Chromium (`caches.open` lève, « Could not create a directory to hold the index file » sur la sortie du programme), tuiles et vignettes ne se gardent plus.
- Le champ « dossier » (`webkitdirectory`) garde 0 fichier quand `DOM.setFileInputFiles` lui donne une liste, sous Chrome comme dans le programme : cette voie ne se teste pas ainsi (`exe-import`).
- Fermeture avec un brouillon : `node outils/banc/exe-fermeture.mjs <Gtracker.exe>` (lance lui-même le programme ; `taskkill /PID` sans `/F` ; un vrai clic du protocole d'abord, Chromium ne retient la fermeture qu'après une action de l'utilisateur ; navigation interne seulement, sauf les essais « page rechargée »). Tuiles gardées : `exe-tuiles`. Import de fichiers du disque : `exe-import`.
- Mémoire du programme : chaque instance du lanceur reçoit une mémoire prête, un dossier neuf `<profil>-memoire` retenu d'avance (`GTRACKER_MEMOIRE`), si bien que les scripts trouvent une mémoire sans passer par la carte du Profil, comme Chrome avec son OPFS. `records()` de `lib/cdp.mjs` lit alors ce dossier par Node (`GTRACKER_MEMOIRE` est passée au script) ; un script qui lit ou écrit la mémoire par `navigator.storage.getDirectory()` y voit une racine qui ressemble à celle de l'OPFS (`window.__bancMemoire`, `lib/cdp.mjs`) : le dossier `Gtracker` y est celui du disque, par le pont de la coquille ; `evaluate` réécrit l'expression, un script qui a son propre `Runtime.evaluate` passe son expression par `pourMemoire`. Le chemin complet de ce dossier, montré par la carte Mémoire, est masqué `MEMOIRE` dans les relevés. Variables d'essai de la coquille, lues sous `GTRACKER_BANC=1` seulement : `GTRACKER_MEMOIRE`, `GTRACKER_DOCUMENTS` (remplace Documents ; sans elle, un dossier du profil d'essai : jamais le vrai), `GTRACKER_BANC_DOSSIER` (réponse de la fenêtre « Choisir un autre dossier » ; vide : renoncement) ; `OneDrive` (variable ordinaire de Windows) pour essayer l'avertissement.
- Mémoire sur le disque : `node outils/banc/memoire-disque.mjs <Gtracker.exe>` (hors registre, lance lui-même le programme, une instance par essai, tout sous `%TEMP%\gtk-mem-*`, effacé à la fin). Sept cas, constatés par Node sur le disque (le septième, la corbeille de 30 jours : `SCRIPTS.md`) : proposition sans rien écrire puis « Utiliser ce dossier » et import (marqueur, `LISEZMOI.txt`, le fichier de réglages de l'appareil, GPX et fiche, le fichier du profil qui retient le dossier, aucun `.gtracker-tmp` ni `.gtracker-new`), second lancement ; dossier renommé (« introuvable », rien recréé, « Réessayer ») ; mémoire façon téléphone (fiche créée) ; temporaires orphelins réparés ; Documents sous OneDrive ; refus d'un sous-dossier `sessions`.
- Liaison sans câble : `node outils/banc/exe-sansfil.mjs <Gtracker.exe>` (hors registre, lance lui-même le programme, `%TEMP%\gtk-sf-*`). Un faux téléphone en Node (`bureau/fauxTelephone.ts`, compilé avec le programme) se présente au serveur du programme, qui n'écoute en mode d'essai que sur 127.0.0.1 (`GTRACKER_BANC_SANSFIL_*`) ; code et port lus sur la page. Le faux téléphone se joue ancien (`ancien: true` : lecture seule, jamais écrit), à jour (il annonce qu'il écrit : provisoires, `valider`, `effacer`) ou qui enregistre (`enregistre: true`) ; `coupureApresEcritures` et `falsifier` règlent les coupures. `BANC_CAS=4,5` ne joue que ces cas. `SCRIPTS.md` dit les six cas.
- Synchronisation avec le téléphone : `node outils/banc/exe-synchroniser.mjs <Gtracker.exe>` (hors registre, lance lui-même le programme, `%TEMP%\gtk-syn-*`, environ 7 min). Un dossier du disque joue le téléphone (`GTRACKER_BANC_TELEPHONE`, lu et écrit comme par le câble ; état et coupure imposés par `GTRACKER_BANC_TELEPHONE_ETAT` et `GTRACKER_BANC_TELEPHONE_COUPURE`), les copies de sécurité vont sous `GTRACKER_DOCUMENTS`. Les deux côtés se lisent par Node. `BANC_CAS=c,g,m,i` ne joue que ces cas (reprise d'un cas : 1 à 3 min au lieu de 9). `--sansfil` rejoue les cas c, r et rg sur le faux téléphone du Wi-Fi à la place du dossier-téléphone du câble, mêmes contrôles (environ 2 min) : `node outils/banc/exe-synchroniser.mjs <Gtracker.exe> --sansfil`. `SCRIPTS.md` dit les cas.
- Application du téléphone : `node outils/banc/exe-application.mjs <Gtracker.exe>` (hors registre, lance lui-même le programme, `%TEMP%\gtk-app-*`, environ 4 min). Variables d'essai de la coquille, lues sous `GTRACKER_BANC=1` seulement : `GTRACKER_APK` (l'APK proposée ; fichier absent : pas d'application), `GTRACKER_BANC_APK_DESTINATION` (réponse de la fenêtre « Enregistrer sous » ; vide : renoncement), `GTRACKER_BANC_APPLICATION_REFUS` (refus imposé à l'installation) ; une installation réussie copie l'APK dans `applications-installees` du faux téléphone (`GTRACKER_BANC_TELEPHONE`). `SCRIPTS.md` dit les cas.
- Matériel des deux appareils : `node outils/banc/exe-materiel.mjs <Gtracker.exe>` (hors registre, lance lui-même le programme, `%TEMP%\gtk-mat-*`, environ 3 min). Le programme écrit lui-même son fichier de réglages (« pc » dans `reglages/`) ; profil et mémoire de la préparation sont recopiés pour chaque cas, un faux fichier d'autre appareil (« telephone ») est posé dans le même dossier. Les gestes (copier, réunir, supprimer, « Reprendre le matériel ») se constatent sur le disque, une fois l'écriture différée (environ 2 s) passée, et les fiches de `sessions/` doivent rester identiques à l'octet. `SCRIPTS.md` dit les cas.
- Piège, `taskkill` sans `/F` et fenêtre cachée : après tout chargement de document (`Page.navigate`, `Page.reload`, `location.reload()`), Chromium ajoute au processus une seconde fenêtre cachée sans titre (classe Chrome_WidgetWin_0 de Windows), placée avant celle de l'application ; toutes deux cachées, la demande de fermeture part vers elle et le programme reste ouvert, sans que la coquille voie rien (pas d'événement `close`).
  Ce n'est pas un défaut du programme : fenêtre montrée, la fermeture marche après un rechargement (`exe-fermeture`, essais D à F). Pour essayer la fermeture après un chargement, lancer avec `GTRACKER_BANC_MONTRER=transparente` (fenêtre montrée sans prendre la main, opacité nulle : rien ne s'affiche) ; `1` la montre vraiment.

## Bibliothèque

`lib/cdp.mjs` (sans dépendance) remplace le harnais que chaque script recopiait ; tous les scripts du registre sont écrits dessus. Les noms de l'application (clés de l'appareil, caches, formats, dossier mémoire, poignée du retour) y sont des constantes exportées (`CLES`, `CACHES`, `FORMATS`, `FICHIER_MARQUEUR`, `DOSSIER_MEMOIRE`, `POIGNEE_RETOUR`, `DOSSIER_BANC`) : un script n'en écrit aucun en dur, car une clé fausse ne casse rien et le script passe à tort.

- `const b = await connect({ port, width, height, shotDir })` ouvre un onglet (`/json/new`), active la console (erreurs et avertissements dans `b.logs`, comme avant), accepte les dialogues, bloque ce qu'on lui donne par `b.blockNetwork(BLOCKED_URLS)` (le réseau est déjà activé). `BASE` a une seule valeur par défaut, `http://localhost:5174`. Avec `BANC_WS=<websocket d'une page>`, il se branche sur cette page au lieu d'en ouvrir une (prévu pour un lanceur). `isolated: true` ou `BANC_CONTEXTE=1` (essai, pas le défaut) ouvre l'onglet dans un contexte neuf (`Target.createBrowserContext`) : localStorage et OPFS vides comme sur un profil neuf, jetés à la fermeture, plusieurs scripts sur un même Chrome (`general.mjs` deux fois de suite : sortie identique).
- Rendu : `send`, `evaluate`, `go`, `settle`, `waitFor`, `wait`, `vwait`, `importGpx(texte, nom)`, `importFiles(chemins Windows)`, `records()` (fiches JSON de l'OPFS), `dumpText()`, `shoot(nom)`, `mouse`, `click(sélecteur ou expression)`, `clickText(texte, sélecteur)`, `check(quoi, ok, détail)`, `finish('Tout passe.')` (message ou nombre d'échecs, onglet fermé, code 0 ou 1), `close`, `onMessage` (événements propres au script).
- `settle({ max })` attend une page prête au lieu de dormir : document chargé, racine React non vide (sous charge, le premier rendu peut suivre le chargement), aucun fetch ni requête (scripts, styles, polices ; pas les images) en vol, aucun `setTimeout` d'au plus 1 s en attente, DOM immobile depuis 150 ms, puis deux images. Un script injecté dans chaque document compte tout cela. `max` est l'ancien sommeil : au pire on retrouve le temps d'avant. `go(chemin, max = 3000)` navigue, attend le **nouveau** document puis `settle` (plafond total `max`).
- `waitFor(expr, { timeout, every })` : expression de la page ou fonction de Node, répétée jusqu'à une valeur vraie ; à l'échéance elle rend la dernière valeur sans lever, le `check` dit l'échec.
- Import : l'écriture en mémoire (OPFS) ne touche ni au DOM ni au réseau, `settle` rendrait la main trop tôt. Après `importGpx` ou `importFiles`, un `waitFor` sur `records()` (la fiche attendue), puis un `settle` court pour sa réécriture différée (800 ms).
- `TEMPS=k` (`lib/horloge.mjs`) accélère l'horloge de la page k fois : `Date`, `performance.now()`, `setTimeout`/`setInterval`, `requestAnimationFrame` ; ni les transitions CSS ni l'horodatage des événements. Un rejeu ×1 tourne k fois plus vite avec les mêmes chiffres (un rejeu de 65 s passe à 7 s à `TEMPS=10`, fiche et général identiques). Le premier `AudioContext` du navigateur coûtant 600 ms réels (soit 6 s de page à ×10), `connect()` en ouvre un et le ferme dès que `TEMPS` > 1. `vwait(ms)` attend `ms` du temps de la page (`ms / TEMPS`) ; `wait` reste le vrai temps.
- Diagnostics sur stderr seulement (`settle /voile 410 ms (plafond 3000)`, un plafond atteint avec sa cause, la durée totale) : stdout reste le relevé qui prouve la neutralité. `BANC_DIAG=0` les coupe.
- Reprise d'un script : même déroulé, mêmes `check`, même sortie standard (comparée par `diff` avant et après, chacun sur un profil neuf) ; `go` garde son ancien délai comme plafond ; un `wait(≥ 800)` qui suit une action devient `settle({ max: N })` ; l'attente après un import devient `waitFor` sur `records()` ; les petits `wait` (glissés, animations courtes) restent.
## Prouver qu'un changement est neutre

`node outils/banc/passe.mjs <noms…> --avant HEAD` (ou `--pages`) : chaque script tourne sur un profil neuf contre le dernier commit et contre l'arbre de travail, et le tableau dit `identique` ou montre le diff. Pour un nettoyage ou une conversion, le relevé doit être identique au caractère près. Un script modifié se rejoue contre son ancienne version par `--avant HEAD --scripts-par-cote`.

## Pièges

Ce que l'agent `banc` et Claude doivent savoir, en plus de la mise en place : les pièges de tout poste, puis ceux du poste de développement. Tout est ici et nulle part ailleurs : un sous-agent ne voit pas la mémoire automatique de Claude.

### Pièges généraux

- Sous charge du lanceur (passage complet), un script peut ne pas trouver le champ d'import dans ses 3 s (« import : absent », puis tous ses ÉCHEC) : le même script joué seul (`passe.mjs <nom> -j 1 --sans-cache`) passe et rend un relevé identique. Le lanceur le fait seul (rejeu, `BANC_CHARGE`, ci-dessus). De même `balises` : un compte de bips qui change d'un, un pixel de glisser, pas un écart du code.
- Sans `--avant <commit>`, le lanceur ne joue que l'arbre de travail et chaque ligne du tableau dit « (avant absent) » : le passage n'a rien comparé, à refaire avec `--avant HEAD`.
- Serveur Vite neuf : le premier chargement compile tout et dépasse les 3 s d'attente des scripts (page vide, « Cannot read properties of undefined ») : charger une page une fois avant de lancer un script.
- Deux serveurs Vite sur une même jonction `node_modules` se disputent `node_modules/.vite` (504 « Outdated Optimize Dep ») : donner un `cacheDir` propre au serveur « avant ».
- Tous les scripts prennent le port Chrome en premier argument ; la plupart n'ont pas d'option `DUMP=` (copies `*-d.mjs` dans le brouillon).
- Une session qu'un script veut importer se fabrique avec `lib/traces.mjs` (`traceVoile`, `traceSurf`…), jamais avec un fichier à fournir ; les noms de l'ancienne application n'apparaissent jamais dans `outils/` (la porte d'import lit les octets de `src/test/legacyImport.fixture.ts` par `charge-ts.mjs`).
- Le texte de page n'inclut pas un tableau replié : pour les podiums de manœuvres, une copie du script dans le brouillon clique « Détails des manœuvres » avant le relevé.
- Rejouer l'analyse hors navigateur, sans Vitest : `node --import <hook>` où le hook (`registerHooks` de `node:module`) ajoute `.ts` aux imports relatifs ; Node lit le TypeScript du projet tel quel. Les sessions réelles du PC se lisent en lecture seule dans la mémoire de l'utilisateur, avec les réglages du hook recopiés.
- Un bug non reproduit vient souvent d'un état de l'utilisateur (onglets graphiques ouverts, mémorisés dans `gtracker.sections`) : demander tôt l'erreur de console et reproduire son état persistant.

### Pièges du poste

Propres au poste de développement (Windows 11, Git Bash, téléphone branché, outils de Claude).

- Brouillon pour les GPX, profils Chrome et relevés : le scratchpad de la session, jamais le dépôt.
- Un serveur lancé en arrière-plan par `npx vite …` survit à l'arrêt de la tâche (seul `npx` s'arrête) : vérifier le port (`netstat -ano`), et tuer le processus node à la fin. Tant qu'il tourne, `npx vitest run` peut échouer sur tous les fichiers (« reading 'config' ») : d'où `npm run verif` et le banc jamais en même temps.
- Le `npm run dev` de l'utilisateur écoute sur `[::1]:5174` (IPv6 seul) : le Chrome du PC l'atteint, pas un `adb reverse` (IPv4). La WebView de l'application refuse le HTTP en clair ; pour un serveur de développement sur le téléphone, passer par Chrome Android (son socket DevTools) et un serveur `--host 127.0.0.1` sur un autre port. Ne jamais toucher aux autres onglets de l'utilisateur.
- Sous Git Bash, un argument `/chemin` passé à un script devient un chemin Windows (« Cannot navigate to invalid URL ») : `MSYS_NO_PATHCONV=1`. `DUMP=` et `SHOT=` : chemin relatif au dossier courant ; un chemin `/c/...` sous `MSYS_NO_PATHCONV=1` devient `C:\c\...`.
- `shots.mjs` remplace `?`, `=`, `:` et `&` dans le nom de la capture ; pour un nom précis, faire la capture par un petit script du brouillon.
- Grosses captures (images de `partage.mjs`, jusqu'à 1,2 Mo) : lues en taille réelle, elles ont coupé deux sessions (ECONNRESET) ; les réduire d'abord en JPEG de 540 px dans le brouillon (System.Drawing en PowerShell, enregistrement en JPEG qualité 75), puis lire une copie à la fois.
- Écran du vrai téléphone : `adb exec-out screencap -p > x.png`, puis lecture de l'image (pas de PIL). Prévenir l'utilisateur avant (écran possiblement verrouillé, notifications privées).
- Un heredoc dont le texte compte un nombre impair d'apostrophes échoue sous le Bash de Claude (« unexpected EOF ») : écrire le script dans un fichier du brouillon. Un `\'` à écrire dans un fichier .ts depuis un script Node en heredoc ressort `'` : corriger ces lignes avec l'outil Edit. Un `node -e "…"` en Bash avale les accents graves.
- Neutralité contre la version commitée sans toucher au dépôt : `git worktree add --detach <brouillon>/avant <commit>`, jonction `node_modules` vers celle du dépôt (`New-Item -ItemType Junction` en PowerShell ; `mklink` sous Git Bash échoue), Vite sur un autre port ; à la fin, retirer la jonction (`rmdir`) **avant** `git worktree remove --force`. Un relevé qui quitte une page à itinéraire non enregistré doit accepter le dialogue `beforeunload`, sinon il se bloque.
- Worktree « avant » à jonction `node_modules` : depuis le 22/10, les polices viennent de `@fontsource` et Vite refuse de les servir (« outside of Vite serving allow list ») ; la version d'avant retombe sur une police de secours et les relevés diffèrent pour rien. Lancer ce serveur avec un fichier de config Vite posé dans le worktree, qui reprend `./vite.config` et ajoute `server.fs.allow: ['.', '<dépôt>/node_modules']`. Vérifier par `document.fonts` : tout en `loaded`. (Cette config est générée par `passe.mjs`, dans `<brouillon>/vite/<côté>.config.mts` : à poser à la main seulement hors du lanceur.)
- Même symptôme, autre cause (13/11, textes du côté « avant » environ 7 % plus étroits : « Statistiques » 76 px contre 87, `tailles` et `aides` « différent » sur un arbre intact) : sous Windows, Vite sert un fichier hors de sa racine (`/@fs/D:/…`) en retirant la lettre du lecteur et en le cherchant sur le lecteur du **dossier de travail** du processus. Le worktree « avant » est dans `%TEMP%` (C:), le `node_modules` du dépôt sur D: : les quatre `inter-latin-*.woff2` répondaient `200 text/html` (la page d'accueil), `document.fonts` donnait `error`, et le texte retombait sur la police de secours, alors que le côté « après » (dans le dépôt, polices servies sous la racine) chargeait Inter. L'autorisation `fs.allow` n'y change rien. Parade, dans `passe.mjs` : Vite démarre avec le dossier du `node_modules` pour dossier de travail et la racine de l'arbre servi donnée par `root` dans la config générée ; et le préchauffage lit `document.fonts` de chaque côté et arrête le passage (« police(s) non chargée(s) côté … ») si une police est en `error`. `settle` attend aussi `document.fonts.status` ≠ `loading`. À la main, hors du lanceur : mêmes précautions (lancer Vite depuis le lecteur de `node_modules`, ou garder le worktree sur ce lecteur, par `--brouillon`).
